# 事前準備
## 1.ドキュメント・ソースコード受領
実際の成果物を基に、実装予定のテスト項目が全て適切に動作するか確認する。

## 2.詳細な業務フローヒアリング
リーダー、あるいは開発者に業務フローをヒアリングする。

## 3.要件定義書・仕様書受領
QAチェックリストでカバーできるレベルの成果物になっているかを確認する。
充分でない場合は各成果物のクオリティを上げる。

## 4.テスト仕様書作成用のSkill作成
ドキュメントを基に、回帰テストが可能なPlaywrightコードを生成するSkillを作成する。
改修案件であれば現行ソースを基に作成する。
要件定義が曖昧であれば、クリティカルのみチェックリストを提示し、残りは正常系のみテストする。

## 5.QA観点盛り込み用のSkill作成
既存のSkillに組み込めるように作成する。
観点：
* テストを前提としてドキュメントを遵守して実装する
* テストコードを作成する前提の設計で開発を進める

## 6.Git導入
リポジトリの構成、PRの頻度を相談する(理想は機能ごと)

## 7.ワークフローの雛形作成
Playwrightのテストを定期実行(22時)するものを作成する

## 8.PR運用(できない前提)
mainへ直接pushでも良しとする場合は他の静的解析で破壊的なpushを制限する仕組みを検討する。
E2Eを薄く、静的解析を厚くしたいためPHPCS導入
Composer公式サイトからComposerをインストール
```bash
composer require --dev squizlabs/php_codesniffer
composer require --dev wp-coding-standards/wpcs
composer require --dev dealerdirect/phpcodesniffer-composer-installer
vendor\bin\phpcs -i //動作確認
```

## 9.バグチケット
不具合やブロックがあった場合、タスク単位でどう管理し、消化するかを相談する

## 10.業務フロー整理
制作側リーダーに全行程を提示し、了承を得る

## 11.環境構築
デザイナーがスムーズに運用開始できるよう資料を整理する


# テスト運用
事前準備が全て揃った状態で、実案件で一連の業務フローを流す
都度フィードバックをもらいながらすすめる

# 全体共有
テスト運用で問題が無ければ、全体で運用開始するために目的・設定方法・業務フローを周知する
